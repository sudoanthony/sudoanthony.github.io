Windows / Active Directory

Most Windows and AD compromises are not exploits - they are legitimate features and rights being used exactly as designed, just by the wrong person. These four concepts chain together into the classic easy-box path: a privilege you shouldn't have lets you read the file that holds every password hash, and a hash is all Windows needs to log you in. They came up on Baby.

What a Windows account is actually allowed to do

Access tokens & privileges

what it is

Every process on Windows runs with an access token that describes who you are: your user SID, the SIDs of every group you belong to, and a list of privileges. Privileges are specific rights that sit outside normal file/object ACLs - things like "back up any file" or "debug any process". You can see your own with whoami /priv and your groups with whoami /groups.

the dangerous ones

A handful of privileges are effectively "local admin" if you hold them, because they can be turned into full control:

SeBackupPrivilege / SeRestorePrivilege - read / write any file regardless of ACL (covered below). SeDebugPrivilege - open any process, including LSASS, to read credentials from memory. SeImpersonatePrivilege / SeAssignPrimaryTokenPrivilege - impersonate another token, the basis of the "Potato" family of attacks that commonly hit service accounts. SeTakeOwnershipPrivilege, SeLoadDriverPrivilege, and SeTcbPrivilege round out the list.

why it matters

These privileges are usually granted through group membership, not assigned directly. Backup Operators grants SeBackupPrivilege; many service accounts carry SeImpersonatePrivilege. So a seemingly "standard" user who happens to be in the wrong group is one command away from the whole machine. The first move after any Windows foothold is whoami /priv and whoami /groups.

hardening / remediation

Least privilege: audit who is in powerful groups (Backup Operators, Server Operators, Print Operators, DnsAdmins), and don't hand backup/debug/impersonate rights to normal user accounts. On a domain controller, membership in any of those groups should be treated as Domain Admin.

seen in Baby - a standard user in Backup Operators held SeBackupPrivilege, visible straight away from whoami /priv.

Read any file, including the ones with the passwords

SeBackupPrivilege

what it is

SeBackupPrivilege exists so backup software can copy every file on a system, even ones the operator has no ACL access to. It grants read access to any file, full stop. That is fine for a trusted backup job, and a disaster when a normal user has it, because "any file" includes the files that store credentials.

how it's abused on a DC

The target is C:\Windows\NTDS\NTDS.dit (the AD database) plus the SYSTEM registry hive (the key that decrypts it). The hive copies out with a plain reg save HKLM\SYSTEM system.hive, but NTDS.dit is a live database and is locked, so a direct copy fails with "being used by another process". The fix is a Volume Shadow Copy: a frozen snapshot of the volume where the file isn't locked.

:: diskshadow script - snapshot C: and mount it as Z:
set context persistent nowriters
add volume c: alias cdrive
create
expose %cdrive% z:

Then read the file out of the snapshot in backup mode (/b), which is what tells Windows to honor the backup privilege and skip the ACL:

diskshadow /s script.txt
robocopy /b Z:\Windows\NTDS . ntds.dit
why it works

The privilege is "read any file" by design - there is no bug to patch. Backup mode on the copy tool is the switch that invokes the right. The shadow copy only exists to get around the file lock on a database that is always open.

hardening / remediation

On a domain controller, treat Backup Operators (and SeBackupPrivilege) as equivalent to Domain Admin. Remove normal users, scope backup rights to dedicated service accounts, and monitor/alert on shadow-copy creation and direct access to the NTDS directory.

seen in Baby - shadow-copied the volume with diskshadow and pulled NTDS.dit + SYSTEM out with robocopy /b.

The Active Directory database - every domain hash

NTDS.dit

what it is

NTDS.dit is the Active Directory database, stored on every domain controller at C:\Windows\NTDS\. It holds all domain objects, and crucially the password hashes and Kerberos keys for every account in the domain - users, computers, service accounts, Administrator, and krbtgt. The hashes are encrypted with a boot key kept in the SYSTEM hive, which is why you need both files.

why it matters

Dumping it is total domain compromise. You get the Administrator hash (instant Pass-the-Hash), and the krbtgt hash, which allows forging Golden Tickets - arbitrary Kerberos tickets that persist even after passwords are reset. It is the single highest-value file in an AD environment.

how it's read

Offline, with Impacket's secretsdump given the database and the boot key:

impacket-secretsdump -ntds ntds.dit -system system.hive LOCAL

The same tool can pull hashes over the wire (DCSync) if you already hold replication rights on the domain, no file copy needed.

hardening / remediation

The file is only reachable by SYSTEM, administrators, or accounts with backup rights, so the defense is guarding those paths (see SeBackupPrivilege above). Detection matters most here: alert on shadow-copy creation, direct NTDS file access, and DCSync-style replication from non-DC hosts.

seen in Baby - NTDS.dit + SYSTEM dumped offline with secretsdump to recover every domain hash.

You don't need the password, just its hash

Pass-the-Hash

what it is

Windows NTLM authentication proves you know a password by proving you hold its NT hash - the plaintext is never sent and never needed. So an attacker who has recovered an account's NT hash can authenticate as that account directly, with no cracking. The hash is the credential.

how it's used

Most Windows tooling accepts a hash in place of a password:

evil-winrm -i IP -u Administrator -H <nthash>
impacket-wmiexec -hashes :<nthash> Administrator@IP
nxc smb IP -u Administrator -H <nthash>
why it works

NTLM is a challenge-response built on the hash, not the plaintext, so holding the hash is cryptographically equivalent to knowing the password for that protocol. This is a design property of NTLM, which is why the whole industry is pushing toward Kerberos and hardening the places hashes live.

hardening / remediation

Protect hash material at the source (LSASS memory, NTDS.dit) and shrink where it ends up: limit which machines privileged accounts log on to (so their hashes aren't left on workstations), enable Credential Guard and the Protected Users group, tier administrative accounts, and disable NTLM where Kerberos can be used instead.

seen in Baby - the Administrator NT hash from NTDS.dit used with evil-winrm -H for an Administrator shell, no password.
