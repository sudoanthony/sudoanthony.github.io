AllSafe

Mobile Medium red team | Android · Allsafe (infosecadventures.allsafe) | [ date ]
tl;dr

Allsafe is an intentionally-vulnerable Android app I used as a stand-in for a real engagement, worked statically on a Pixel 5 AVD (API 33) with jadx, apktool, and MobSF. Recon and static analysis alone surfaced a hardcoded secret reached through R.string.key, an exported DeepLinkTask activity reachable from the open web, insecure logging of the full deep-link URI, and a debug/backup misconfiguration in the manifest — all before ever running the app.

01Recon & Static Analysis

MASVS: CODE, PRIVACY  ·  Mobile Top 10: M2, M8  ·  Handbook ch.2

AllSafe is a stand-in for the real apps we would test in the field. In a real engagement we usually get:

  • The binary — the client emails us the APK/IPA or gives us a TestFlight/Firebase build. "Binary" just means the compiled app file: the .apk on Android or the .ipa (containing a Mach-O) on iOS. Not the phone.
  • Test accounts — credentials for staging environments.
  • Scope & rules of engagement — which backends we can and can't touch.
  • An authorization letter — the paperwork that makes the testing legal.

For the lab, we stood up a Pixel 5 emulator, set Burp as a proxy and pointed the device at it, exported our CA and pushed it to the Pixel 5, and confirmed we can see decrypted HTTPS traffic. We installed AllSafe on the device and pulled the APK back. Our two static workhorses are jadx and apktool.

Tools used: Android Studio (Pixel 5 AVD) · jadx · apktool · Windows PowerShell · Burp Suite Community · MobSF

1 · Peek at the structure

We could jump straight to decompiling, but it pays to know exactly what we're holding first.

  • How big/complex is it — one classes.dex or six?
  • Are there native libraries? If so, that's where Reverse Engineering comes into play.
  • Are there assets or raw resources? (Our peek finds them immediately.)
  • Is it packed/obfuscated? Spotting weird filenames, an encrypted dex, or a loader stub early saves a lot of wasted time.
what's a loader stub A loader stub is what you find instead of real code when an app is packed (protected/obfuscated by a commercial packer). The real code is encrypted into an assets/ blob or a .so instead of a normal classes.dex, with a tiny loader whose only job is to decrypt the real dex and load it into memory at runtime. Static analysis can only go so far when the visible dexes are empty, there's an encrypted blob in assets, or a suspicious native lib — dynamic analysis (later) lets us dump the real dex from memory.

3 · Review the manifest

Navigate to Resources → AndroidManifest.xml — the app's blueprint. It declares every component, permission, and exported entry point, so it's the first thing to read on every test.

We're hunting for specific flags that point at interesting behaviour.

Risky manifest flags

  • android:debuggable="true" — a debug build shipped to production. Anyone can attach a debugger, run code as the app, and read its memory. Should never be set in a release.
  • android:allowBackup="true" — app data can be extracted over ADB with adb backup, no root needed. Leaks whatever the app stores locally.
  • android:networkSecurityConfig — points to an XML file defining trusted CAs, cleartext exceptions, and pinning. Its absence (plus cleartext on) is itself a weak posture.

android:exported="true" on activities / services / receivers / providers means other apps can invoke the component. Keep in mind some are exported by design and benign — like the ProfileInstallReceiver above (an androidx library component). We focus on the app's own components.

The real lead is an exported <activity> whose intent-filter contains VIEW + BROWSABLE + a custom <data android:scheme="allsafe">. That combination = reachable from any web page. The line <activity android:name="...challenges.DeepLinkTask"> names the class — it tells us where to read.

So we jump to infosecadventures.allsafe.challenges.DeepLinkTask in jadx.

We start at onCreate() — the method Android calls the moment the activity launches, and where the incoming Intent and its URI get received and read:

  • getIntent()
  • intent.getData()
  • data.getQueryParameter("key")

That gives us the data flow. The BROWSABLE filter we saw earlier means an attacker controls the URI that starts the activity. When it starts, onCreate runs — so this is the first place attacker-controlled input is consumed.

From here we see a getString(R.string.key). To explain it: R.string.key isn't the secret — it's a label that says "go look up the string named key." The actual value lives in a separate resource file, strings.xml. So the code is saying "compare the user's input to whatever's stored under key," and Android fetches the real value at runtime.

the analogy Think of R.string.key as a locker number and strings.xml as the locker. The code only shows you the number; you have to open the locker to see what's inside. The secret was in the locker the whole time — the developer just didn't write it directly on the door.

And strings.xml ships inside the APK exactly like the code does, so anyone with the app can read it — the developer only added one hop of indirection. That hop is also why a keyword grep (and our MobSF pass in step 5) miss it: both scan the code, and the value is a random UUID with no telltale word like "password." The only way to catch it is to notice the R.string.key reference and follow it into strings.xml.

4 · Hunt for secrets

Now we cast a wide net across the decompiled source with a keyword grep:

Get-ChildItem -Recurse -File C:\Users\Anthonby\Desktop\allsafe-src\sources\infosecadventures\allsafe |
  Select-String -Pattern "password|secret|api[_-]?key|token|http://|s3\.amazonaws|firebaseio\.com|BEGIN (RSA|EC|PRIVATE)"

Nearly half of what comes back is R.java — auto-generated resource IDs (passwordToggle..., google_api_key = 0x7f13004f), not the values we want. So we tighten the search:

Get-ChildItem -Recurse -File C:\Users\Anthonby\Desktop\allsafe-src\sources\infosecadventures\allsafe |
  Where-Object { $_.Name -ne 'R.java' } |
  Select-String -Pattern "password|secret|api[_-]?key|token|http://|s3\.amazonaws|firebaseio\.com|BEGIN (RSA|EC|PRIVATE)"

5 · MobSF — the automated first pass

MobSF runs all of the above automatically and produces a scored report. I used mobsf.live to upload the APK and run the analysis.

The report gives us, in one place:

  • A manifest analysis (every flag from above, tagged with severity)
  • A secrets / hardcoded-strings list
  • Detected trackers and third-party SDKs (the M2 supply-chain view)
  • A permission breakdown
  • …and an overall security score. (It does the same for iOS .ipa files.)
MobSF is a first pass, not the test Automated tools find the obvious and miss the interesting. MobSF catches debuggable and a literal password = "...", but it won't understand that an exported activity bypasses a login, or that a "random" token is derived from the device ID. Use it to triage fast, then read the code yourself — a report that's only a MobSF export is not a pentest. It's exactly why our hardcoded UUID from earlier slipped past it: no keyword, and it lives in resources, not source.

These are a representative few — static analysis surfaced more across the app (hardcoded SOAP credentials, a base64 auth token, a hardcoded AES key, a Firebase API key), but they show the method end to end. Severity is tied to what each issue actually authorizes in this app.

SeverityLow — the key only gates a local "congrats" screen; the same pattern guarding a real API key would be Critical.
DescriptionA deep-link query parameter is compared against a secret fetched with getString(R.string.key). The value is a hardcoded UUID stored in res/values/strings.xml (compiled into resources.arsc) — a resource, not source code.
ImpactThe secret ships inside the APK, so anyone with the file recovers it offline — no device, no root — by following the R.string.key reference into strings.xml. A keyword grep and MobSF both miss it.

TitleExported activity reachable via BROWSABLE deep link
SeverityMedium — unauthenticated, web-reachable entry point; exposed to any app or web page.
DescriptionDeepLinkTask is exported with a VIEW + BROWSABLE intent-filter on the allsafe:// scheme, so any app — or a link on any web page — can invoke it with attacker-chosen URI data.
