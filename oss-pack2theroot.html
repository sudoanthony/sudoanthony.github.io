Pack2TheRoot: a umask-dependent build failure

gbuyssens/CVE-2026-41651 / PR #1 / open / 2026-11-21
tl;dr

Pack2TheRoot is a PoC for a PackageKit TOCTOU local privilege escalation (CVE-2026-41651). Before it can even attempt the race, it builds a malicious .deb package, and that step was failing outright. The script creates the package's control directory with os.makedirs() and never sets its permissions explicitly, so they come straight from the calling process's umask. In a non-interactive shell context where umask is 0, the directory lands at 777 and dpkg-deb --build refuses to package it. The fix is a one-line os.chmod() right after creation.

01The failure

Running the script where umask was 0, the very first step, building the payload .deb, failed:

$ python3 exploit.py
dpkg-deb: error: control directory has bad permissions 777
(must be >=0755 and <=0775)

Nothing about the target mattered yet. This is the script failing to build its own payload, before any D-Bus call or race condition comes into play.

02Root cause

The relevant code:

debian = f"{d}/DEBIAN"
os.makedirs(debian, exist_ok=True)

with open(f"{debian}/control", "w") as f:
    f.write(...)

os.makedirs() does not set a directory's permissions outright. The mode it ends up with is whatever the calling process's umask leaves after masking whatever default mode Python requests. In a normal interactive login shell, umask is usually 022, which leaves the directory at 0755 and nobody notices anything is wrong. But a non-interactive shell, which is exactly what a foothold from a web shell or a similar entry point tends to be, very often has umask 0. With umask 0 the directory comes out at 777, and dpkg-deb --build enforces a hard range of 0755-0775 for control directories. The exploit dies right there, before it ever reaches the TOCTOU race it is actually built to win.

03The fix

Stop relying on the ambient umask and set the permissions explicitly, right after creating the directory and the control file:

- os.makedirs(debian, exist_ok=True)
+ os.makedirs(debian, exist_ok=True)
+ os.chmod(debian, 0o755)

  with open(f"{debian}/control", "w") as f:
      f.write(...)
+ os.chmod(f"{debian}/control", 0o644)

Five lines, no logic touched, no behavior change when umask happens to already be 022.

04Proof

Verified locally in a throwaway WSL Ubuntu environment with os.umask(0) set, isolating just the directory-build logic from the rest of the script (no PackageKit/D-Bus involved, this part does not need it):

$ umask 0; python3 test_before.py
dpkg-deb: error: control directory has bad permissions 777
(must be >=0755 and <=0775)
# ... CalledProcessError, build aborts

$ umask 0; python3 test_after.py
Package 'after' in '/tmp/out_after.deb'.
BUILD_OK

Same umask, same logic, only the explicit chmod added. Before: hard failure. After: the package builds. The only remaining output after the fix is an unrelated warning about the build directory's owner/group, expected when not running as root and unrelated to this bug.

05Takeaways

  • A script that assumes umask 022 will quietly break the moment it runs somewhere that is not an interactive login shell. If permissions matter, set them explicitly rather than trusting the environment's default.
  • os.makedirs()'s mode argument is masked by umask; it does not set permissions outright. os.chmod() afterward is the only way to get an exact mode regardless of umask.
  • This kind of bug is easy to miss in testing because an interactive dev shell almost never has umask 0, so the script "just works" right up until it runs somewhere that does.
