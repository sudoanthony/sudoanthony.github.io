Privilege Escalation

Getting a foothold makes you a user; privilege escalation makes you root. On Linux the recurring pattern isn't a single exploit - it's finding a place where something already running with more power than you touches something you can influence. A script root runs on a timer, a file root writes into a directory you own, a service that trusts a path without checking it. The two concepts below are the ones Nexus turned on, and they pair naturally: first you find the automated root job, then you turn where it writes against it.

Automated root jobs · cron & systemd timers

Scheduled jobs

what it is

Most Linux boxes run tasks automatically on a schedule - backups, cleanups, sync scripts. If one of those runs as root and touches anything you can influence (a script you can edit, a file or directory you own, a relative path, a shell wildcard on data you control), it's an escalation path. The job hands root's privileges to whatever it operates on, and you supply that "whatever."

how to find it - check BOTH schedulers

Cron and systemd timers are two separate systems, and it's easy to check one and miss the other. Cover both:

cron: cat /etc/crontab, ls -la /etc/cron.d/ /etc/cron.daily/, and per-user crontab -l. The system tables have a username column - you're hunting a non-default line that runs as root.

systemd timers: systemctl list-timers --all shows what fires and when. For anything interesting, read its .timer and the .service it triggers: a service with no User= line runs as root, and ExecStart= is the exact command it runs. A quick grep -rn 'name' /etc/systemd /etc/cron* ties a suspicious script back to the unit that launches it.

why it works

The scheduler is trusted infrastructure, so admins wire custom scripts into it without thinking of them as an attack surface. The flaw is rarely the schedule itself - it's that the root-run job reaches into a location, script, or input that a lower-privileged user can modify. Once you can change what root executes or reads, you inherit root.

hardening / remediation

Run the job as a dedicated least-privilege user instead of root. Keep the script and every directory in its path root-owned and not group/other-writable. Use absolute paths, avoid wildcards on attacker-influenceable input, and validate anything the job reads from a user-writable location.

Write-redirection · symlink following / TOCTOU

Symlink attacks

what it is

A symlink is just a file that points at another path. When a program opens a path that passes through a symlink, it follows the link without question. So if a privileged process is going to write a file into a directory you control, and you replace part of that path with a symlink pointing somewhere only root can write, root's process follows your link and writes there - as root. You never gain the write yourself; you borrow root's.

how it works

Say a root job writes to /home/git/staging/<name>/authorized_keys and you own /home/git/staging. Pre-create the <name> segment as a symlink:

ln -s /root/.ssh /home/git/staging/name

Now when root writes /home/git/staging/name/authorized_keys, it lands in /root/.ssh/authorized_keys instead. Drop your own SSH public key in and you log straight in as root. Any predictable root-written filename works as the payload - authorized_keys, a cron line in /etc/cron.d/, a config the next root process reads.

Racing the job: if the scheduled job already ran and created a real directory where you wanted your symlink, you can't drop the link inside it. But you own the parent, so move the whole tree aside, recreate the path clean, and place the symlink before the next tick - then let the timer fire.

why it works (TOCTOU)

The privileged writer trusts the path at write-time without checking that no component is a symlink - it never opens with O_NOFOLLOW or lstats the path first. That gap between assuming a path is safe and actually using it is the classic time-of-check / time-of-use (TOCTOU) flaw.

hardening / remediation

Open with O_NOFOLLOW (or resolve and verify the real path before writing), keep the target directory root-owned so no one can plant links in it, and don't have root write into a tree a lower-privileged user controls. Running the writer as a non-root user contains the damage even if a link slips through.

Working privilege escalation

Tools

Enumeration first - most escalations are found, not forced. Manual checks teach you what to look for; the automated scanners just do it faster once you know why.

manual enumeration

systemctl list-timers --all, cat /etc/crontab, sudo -l, id, and find / -perm -4000 -type f 2>/dev/null for SUID. Knowing these by hand is the point - the scanners below just automate them.

pspy

Watches processes and scheduled jobs fire in real time without root - the fastest way to catch a cron/timer job and see the exact command it runs, including the paths it touches. Ideal for spotting a writable-path job.

LinPEAS

Automated Linux enumeration - flags writable cron/timer scripts, SUID binaries, weak permissions, and known escalation paths, colour-coded by likelihood. Great to expedite, but learn the manual checks first so you understand what it's flagging.

ln -s (coreutils)

The symlink primitive itself - no special tool needed. ln -s TARGET LINK creates the pointer; ls -la confirms it reads link -> target before you let the root job fire.

GTFOBins

Reference for turning a specific binary (via sudo, SUID, or a capability) into a shell, file read/write, or command execution - the go-to when sudo -l or the SUID sweep turns up something non-default.
