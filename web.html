Web & Environments

Two things that quietly shape a web engagement: how the target app is being run, and how you go looking for the parts of it that aren't linked anywhere. The same code behaves and fails differently depending on whether it's a raw process, a container, or a fleet of them - and the tool you reach for to map its hidden surface depends on the shape of what you're hunting. Both of these came up the hard way testing Juice Shop.

Where your app actually runs

Running & hosting apps

what it is

"Hosting" just means where and how a program is executed. The same app can run as a bare process on your laptop, inside a sealed container, on a whole virtual computer, or spread across a cluster of machines - and each choice trades off simplicity, isolation, resource cost, and how well it survives being hammered. For a tester, that last part matters: a fragile setup falls over under a scan, a sturdy one shrugs it off.

run it directly (native / npm start)

The app runs straight on a host using a language runtime you installed there - npm start, python app.py, ./binary. Simplest option and best for developing, since you can edit code and watch logs live. Downsides: it's tied to that host's exact versions (the classic "works on my machine"), shares the machine's resources with no isolation, and dev-mode builds are heavier and less stable. If it crashes, nothing brings it back - which is exactly what kept happening to Juice Shop under a directory scan.

virtual machines (VMs)

A VM emulates an entire computer - its own kernel and operating system - on top of yours through a hypervisor (VirtualBox, VMware, KVM). You get strong isolation and can run a completely different OS (your Kali VM, an Android emulator). The cost is weight: gigabytes of RAM and disk and a slow boot, because you're running a second full OS.

containers (Docker)

A container packages an app with its exact runtime and libraries into an image, but instead of booting a whole OS it shares the host's kernel. That makes it far lighter than a VM - megabytes, and it starts in seconds - while still isolated from the host. The image runs identically anywhere, which kills "works on my machine." Prebuilt production images (like bkimminich/juice-shop) are sturdier than a dev npm start, support memory limits and --restart auto-recovery, and are disposable: nuke it and redeploy a clean instance in seconds.

orchestration & serverless

Kubernetes / orchestration runs and scales many containers across many machines, handling restarts, load-balancing, and rollouts automatically - what most real production web apps run on today. Serverless / PaaS (AWS Lambda, Cloud Run, Vercel, Heroku) goes further: you hand over just the code and the platform runs and scales it, even down to zero when idle. There's no server for you to manage - but a different attack surface, like event/injection into functions and misconfigured cloud IAM roles.

why this matters when testing

The runtime shapes both behavior and fragility. A dev npm start can OOM-crash under a scan flood, while the same app's production Docker image takes the load and, with --restart=unless-stopped, heals itself - so on a delicate lab target you throttle hard, and on a robust production target you can push more (but "don't DoS the client" always holds). It also matters after you land a shell: are you inside a container (you may need to escape it to reach the real host) or on bare metal (root really is root)? A quick ls -la /.dockerenv and cat /proc/1/cgroup answers that.

seen in Juice Shop - a dev npm start kept OOM-crashing under directory brute-forcing; switching to the official Docker image with --restart=unless-stopped gave a stable, self-healing target. Nexus - checked /.dockerenv and /proc/1/cgroup to confirm a bare-metal host before escalating.

Finding hidden paths, files & endpoints

Content-discovery tools

what it is

Directory / content brute-forcing (also called forced browsing or content discovery) fires a wordlist of candidate paths at a target to find pages, files, and endpoints that aren't linked anywhere - an admin panel, a backup file, a hidden API, a log directory. It's core recon on any web target, and the tools below all do the same basic job; they differ in how they do it.

the tools, and when each wins

feroxbuster

Fast Rust scanner, recursive by default - finds a directory then automatically digs inside it, surfacing nested paths (/support → /support/logs) in one run. Also auto-extracts links from responses and can save/resume state. Best default for directory/content discovery.

gobuster

Fast Go scanner. Flat (single-level) directory brute-forcing, but it also has dedicated vhost and dns subdomain modes the others lack. Simple and reliable; the pick when you specifically need virtual-host or DNS enumeration. No recursion, so nested paths need a second scan.

ffuf

"Fuzz Faster U Fool" - the Swiss-army fuzzer. Put the FUZZ keyword anywhere: a path, a URL parameter, a header, or a JSON body. Best for parameter fuzzing and brute-forcing POST logins, with rich filtering by size/status/words/regex (-fs, -mc). Hugely flexible; less "point-and-recurse" than ferox.

dirb / dirbuster

The old classics. dirb is a simple CLI with a built-in wordlist; dirbuster is its Java GUI with recursion. Still work, but largely superseded by the speed of the Go/Rust tools.

wfuzz

The original flexible web fuzzer (Python) and the conceptual ancestor of ffuf - same FUZZ-keyword idea for params, paths, and headers. Slower than ffuf, which has mostly replaced it, but still capable.

dirsearch

Python path brute-forcer with smart defaults - good built-in lists and automatic extension handling. A popular, low-friction middle ground.

how to choose (and not DoS the target)

Match the tool to the shape of the hunt: nested directory/content discovery → feroxbuster (recursion); parameter, header, or POST-body fuzzing → ffuf; virtual-host or DNS subdomain enumeration → gobuster. And whatever the tool, two things decide whether you find it and keep the target alive: right-size the wordlist (a small curated list first, escalate to raft/medium only when it comes up empty), and throttle to the target's fragility (low threads, add a delay, and exclude giant responses so you don't re-pull them to death). And know the ceiling: against a SPA, every unknown path returns the same catch-all, so filter by response length (--exclude-length / -fs) rather than status code - but the catch-all also hides real routes. A server path like /support/logs whose parent (/support) is only a client-side route returns the catch-all at that parent, so scanners filter it as 404-like and never recurse in. Sometimes brute-forcing legitimately can't surface a path, and you fall back to reasoning and known-path intuition (logs live under an admin/support area).

seen in Nexus - gobuster vhost mode found the git. and billing. subdomains, and ffuf brute-forced a login. Juice Shop - the SPA catch-all defeated status-based scans (filter by length instead) and even hid /support/logs from recursion, since its parent /support returns the catch-all and gets filtered - so the log path had to be reasoned, not brute-forced; ffuf cracked the admin password against /rest/user/login.
